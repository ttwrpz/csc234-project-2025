## 1. `analyzePatterns` Cloud Function

The new Cloud Function (`functions/src/analyzePatterns.ts`) computes pattern
insights over the user's mood history. Per ADR-0007 the function is
**statistical-primary, Gemini-supplementary**. The Gemini supplementary
call is now wired (post-v1.0 patch — see commit history): when the
history has ≥30 entries, the function calls `analyzeForPatterns()` in
`geminiClient.ts` with a 5s `AbortController` budget, validates the
response via `GeminiThemeResponseSchema`, clamps confidence to
`PATTERN_GEMINI_MAX_CONFIDENCE` (0.7), and appends a `kind: 'gemini'`
insight on success. Any failure (timeout, parse_error,
gemini_unavailable, sample_too_small) is **non-fatal** — the response
still ships with the statistical insights and `geminiSkipped: true` plus
the relevant `geminiSkipReason` is logged.

### 1.1 PII fence — three layers, all verified

The user's mood `text` field is the most sensitive data in the entire app.
The function MUST never receive it. Three independent defences enforce this:

1. **Client datasource projection.**
   `apps/mobile/lib/features/analytics/data/datasources/analyze_patterns_functions_datasource.dart`
   projects each `MoodEntry` to `{ date, moodCode, intensity }` only.
   `static Map<String, Object?> projectEntry(MoodEntry e)` is exported so the
   unit test can assert exact-key equality.
   - **Test**: `analyze_patterns_functions_datasource_test.dart` — 7 cases
     including `expect(out.containsKey('text'), isFalse)`,
     `expect(out.containsKey('mediaRefs'), isFalse)`, exact-key-set
     assertion, and a substring canary against the original text body.
   - **Status**: ✅ verified.
2. **Server Zod schema (`.strict()`).** `AnalyzePatternsRequestSchema` in
   `functions/src/types.ts` rejects unknown keys at the Zod boundary —
   inner `history[]` entries are also `.strict()`. A client that
   accidentally sent `text` would be rejected with `invalid_input` before
   the function did any compute.
   - **Test**: `analyzePatterns.test.ts` cases #2 and #2b — top-level
     `text` and per-entry `text` both rejected.
   - **Status**: ✅ verified.
3. **Server logger allowlist.** `handleAnalyzePatterns` writes a single
   `logger.info({...})` line per request. The allowed fields are
   enumerated explicitly: `event, requestId, uid, outcome, windowDays,
   historyLen, insightCount, statisticalInsightCount, geminiSkipped,
   geminiSkipReason, latencyTotalMs, rateLimit.{remaining, retryAfterSec}`.
   No `history`, no `history[].date`, no insight body text.
   - **Test**: `analyzePatterns.test.ts` case #10 (PII canary) asserts no
     log payload across the 10-case run contains a date prefix
     (`'2026-'`), an insight body string (e.g. `'three or more heavy
     days'`), or the keys `'history'` / `'text'` / `'mediaRefs'`.
   - **Status**: ✅ verified.

### 1.2 Validation order

`handleAnalyzePatterns` mirrors `analyzeMoodText`'s pipeline:
auth → Zod (`.strict`) → rate-limit → statistical compute → respond.
The rate-limit token is consumed BEFORE any optional Gemini call so an
upstream Gemini outage cannot DoS the project's Gemini quota. (Gemini is
not wired in v1.0; this ordering is preserved for the follow-up patch.)

### 1.3 Rate limit

`functions/src/rateLimit.ts` was parameterised in #16 to accept
`{ windowMs, max, collection }`. `analyzePatterns` calls with
`{ windowMs: 30_000, max: 1, collection: 'rateLimits.patterns' }` so the
tighter 1/30s window writes to a separate Firestore doc family
(`rateLimits.patterns/{uid}`) and does NOT collide with `analyzeMoodText`'s
limiter (`rateLimits/{uid}`, 10/60s). A user hitting both endpoints in the
same minute is rate-limited per-endpoint, not per-app, which is the
correct behaviour.

**Operational follow-up (carried over from R-M01, 2026-04-29 audit)**:
verify the Firestore TTL policy is configured against BOTH
`rateLimits.expireAt` and `rateLimits.patterns.expireAt`. The doc-comment
in `rateLimit.ts:73-80` calls this out.

### 1.4 App Check

`analyzePatterns` ships with `enforceAppCheck: true` from day one (per
kickoff Open Question O-1). `analyzeMoodText` retains `enforceAppCheck:
false` until Sprint 5 — the inconsistency is intentional and bounded.
Rationale: the existing `analyzeMoodText` was deployed against
`enforceAppCheck: false` and changing it requires a coordinated rollout
(`debugProvider` setup on dev clients, App Check token attestation on prod
clients). The new function ships strict from inception.

**Severity:** Medium during the inconsistency window. **Mitigation:**
documented in ADR-0003 as a deferred S5 line item.

## 2. Pattern detector and storage (`features/garden/`)

### 2.1 Detector purity

`features/garden/domain/pattern_detector.dart` is pure Dart — no Flutter,
no Firebase, no Cloud Firestore imports. The CI domain-purity check
(`.github/workflows/ci.yml` step "Domain purity check") greps for
forbidden imports under `features/*/domain/` and would fail the build on
violation. Verified clean as of `feat/5.3-5.4-pattern-detection` HEAD.

### 2.2 Storage anchors

`features/garden/data/intervention_state_storage.dart` persists two
ISO-8601 timestamps to SharedPreferences:
- `intervention.last_triggered_at_iso8601` — drives 48h cooldown
- `intervention.first_triggered_at_iso8601` — drives 10-day escalation

Both are **device-local** (SharedPreferences is not synced across devices
in S4). This is acceptable because:
- The detector's correctness is per-device — a user with two devices
  sees the cheer-up banner on each device independently, which matches
  the "rolling visualisation of recency" mental model from ADR-0006.
- No PII in the keys or values — only timestamps.
- The storage is read-only in S4 (the WRITE side lands with the S5
  banner UI), so a malformed value in the wild cannot corrupt anything.

**Severity:** None. No findings.

## 3. Firestore rules — `users/{uid}/insights`

`firebase/firestore.rules` lines 42–45 (Sprint 3 anticipated this in
preparation for Sprint 4):

```
match /users/{uid}/insights/{insightId} {
  allow read: if isOwner(uid);
  allow create, update, delete: if false;
}
```

The `analyzePatterns` Cloud Function does NOT write to this collection in
v1.0 (insights are re-computed per request — see ADR-0007 §"Alternatives
considered"). The collection exists for forward compatibility; the rule
ensures that a) only the owner can read their insights, b) only the
admin SDK (i.e. the Cloud Function) can write, and c) the client cannot
fabricate insights of its own.

**Status**: ✅ verified — no change required for v1.0.

### 4.2 Mobile app (`apps/mobile/pubspec.yaml`)

(SDK). Both are dev-only; production app surface is unchanged. No HIGH /

### 4.3 Repo-wide secret scan

`pre-write` Claude Code hook scans every Write/Edit for embedded secrets;
plus a manual `grep -rE "(AKIA|ghp_|sk-|AIza|pgsql:|mongodb:)" --include=*.{dart,ts,yaml,json,md} .`
on the v1.0 candidate produced no hits. The Gemini API key is bound via
`defineSecret('GEMINI_API_KEY')` in `geminiClient.ts:23` — never read from
`process.env` directly. (Verified by `analyzeMoodText.test.ts` case #14:
"secret loaded via defineSecret, never via process.env".)

**Status**: ✅ verified.

## 5. Demo-only configuration regressions

### 5.1 60-second `minimumFetchInterval`

`apps/mobile/lib/main.dart` lowered Remote Config's
`minimumFetchInterval` from 60 minutes to 60 seconds for the v1.0 demo
kill-switch rehearsal (kickoff Open Question O-3). The change is
documented in `docs/runbooks/feature-flag-rollback.md` §"Restoring the
60-minute interval" with an explicit v1.0.1 follow-up.

**Severity:** Low. Production clients on the v1.0 build would issue ~60×
more Remote Config fetches per hour than v0.3-beta. At MoodBloom's
current install base (single-digit devices) this is a non-event; at any
real-world scale the v1.0.1 patch must ship before the install base
grows.

**Mitigation:** v1.0.1 ticket filed; runbook documents the restoration.

### 5.2 Integration tests are scaffold-only

The `integration_test/` directory ships in v1.0 with one passing flow
(auth_flow_test) and three skipped stubs. The kickoff acceptance bar
demands "integration test for login flow passes on Android emulator AND
Chrome web". Sprint 4's local-only verification satisfies the acceptance
bar; the device matrix lives in Sprint 5's CI track.

**Severity:** None — this is a scope-bounded scaffold, not a security
finding.
